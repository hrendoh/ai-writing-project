# 執筆ガイドライン（トーン＆マナー）

AIエージェントが執筆する際は、以下のガイドラインを遵守してください。

## 1. 文体・トーン
- です・ます調（敬体）を基本とし、一人称は「私」を使用します。
- ターゲット読者：Webエンジニア、技術に興味のある開発者。
- 専門用語は無理に平易にせず、正確な用語を使用してください。
- **事実と意見で文末を書き分けます（最重要）**:
  - 技術仕様・手順など出典のある事実 → 断定調で書く（例: 「イベントを受け取ったら chat.unfurl API を呼び出します」）
  - 著者の考察・感想・推測 → ヘッジ表現で和らげる（例: 「〜のではないかと思います」「〜かもしれません」「〜そうだと感じています」）
- 解説の合間に、読者への口語的な語りかけを適度に挟みます（例: 「いわゆるテストファーストですね」「このあたりは悩みどころですね」）。多用は避け、1セクションに1回程度。
- 重要な用語・機能名・製品名は**太字**で強調します。
- 記事自身を持ち上げる過剰な強調・自己言及表現（例: 「そこが本記事のいちばんの読みどころだと思います」「ここが最大の見どころです」）は書きません（AIっぽさが出るため）。読みどころは宣伝せず、内容そのもので示します。
- 余計な比喩表現を使いません。指す内容が読者にすぐ浮かばないメタファー（例: 「結線」）は避け、そのまま平易に言うか、イメージの湧く言葉（例: 「導線」）を選びます。
- 抽象的な単語でぼかさず、具体的に記述します。総称や曖昧語（例: 「部品」「リソース」「ツール」）で済ませず、指しているものの具体名（例: 「テンプレート」「検証スクリプト」）で書きます。
- 読者に馴染みのない業界用語・術語は、初出で平易な言い換えか一言の説明を付けます（例: 「オナーシステム」→「不正をしないことを受験者の良心に任せる自己申告制」、「コーパス」→「全ページの本文を1つにまとめたファイル」）。比喩的な抽象語（例: 「ゲート」）は、指している動作をそのまま書きます（例: 「配布するかどうかは、このレビューだけで決まります」）。
- 序数は「1つめ」「2つめ」の数字表記で統一します（「ひとつめ」「ふたつめ」は使いません）。
- **指示語は、対象を直前に導入したときだけ使います**。「同じ記事」「先の記事」「あの表」「先ほどの〜」などの照応表現が指せるのは、同じ節内（目安として数段落以内）で導入した対象だけです。次の場合は指示語を使わず、対象の名前（著者名・記事名・図表名など）で再指定します。
  - **節をまたいで参照する場合**（例: 数節前の記事を「先の記事」と呼ぶ → 読者は特定できない）
  - **間に別の候補が挟まる場合**（例: A記事を「同じ記事」と呼んだ後にB記事を導入し、その後再びA記事を「同じ記事」と呼ぶ → 直近のB記事に誤って解決される）
  - **章をまたぐほど距離が遠い場合**は、名前で再指定するだけでなく、位置の目印も添えます（例: 「Böckelerの記事は〜」→「**前半で紹介した**Böckelerの記事は〜」）。
- 事実より強い言い方をしません。次の2種類に注意します。
  - **主観的な度合いの形容**: 検証結果や挙動を語るときに、書き手の感じ方を程度表現として混ぜません（例: 「あっけないほど順調でした」→「順調でした」）。「かなり」「とても」「非常に」のような**程度を強める副詞**も同様に扱います（例: 「かなり楽です」→「楽です」）。所要時間・回数・成否といった事実を並べれば十分です。感想として書きたい場合は、事実の記述とは分けてヘッジ表現で述べます。
  - **確認できない意図・理由の断定**: 自分や他者の動機を、根拠なく断定的に書きません（例: 「意図的に割愛したスキルがあります」→「取り上げなかったスキルがあります」）。理由が事実として言えるなら、その理由を書きます。
  - **著者の動機・心情・経緯も出典の対象**: 「〜が気になって」「味を占めて」「期待して」のように、検証に至った動機やそのときの心情を事実として書く場合は、`NOTE-xx` に記録があることを確認して出典を付けます。記録がない場合は、動機を書かずに行った操作だけを書く（例: 「続いて〜を試しました」）か、`💬 経験談` として明示します。地の文だからといって出典の対象外にはしません。
- 過剰な演出表現を使いません。読者への注目誘導（例: 「3の太字部分に注目してください」）や、「まさに〜」「まるで〜」のような大げさな強調表現は書かず、内容をそのまま述べます。

## 2. 記事の構造
- **読者がメンタルモデルを段階的に構築できる順序で構成します**。記事・章・節のいずれのレベルでも、まず「何についての話か」の全体像を与えてから、背景・詳細に入ります。読者がまだ知らない固有名詞や問題設定を、前提の説明なしに冒頭へ置きません（違反例: 記事の主題であるプロジェクトを紹介する前に、その動機となった過去の出来事の詳細から書き始める）。
- 導入: 記事の主題の概要を短く示し、背景・きっかけを述べてから、「この記事では、〜について解説したあと、〜を紹介します」の形で記事の内容を予告します。
- 見出し: h2中心。体言止めまたは疑問形（例: 「Slackワークオブジェクトとは？」）。
- 見出しは、節の内容の主体を読者が誤解しないか確認します（例: 「人のレビューをどう入れているか」の節に AI の一次レビューも含まれる場合、見出しだけで人だけが行うと読まれないよう、本文の冒頭で二段構えであることを先に示す）。
- 手順は番号リスト、列挙は箇条書きを使います。
- 参照リンクは「参照: [タイトル](URL)」の形式で該当箇所の直後に置きます。
- 引用ブロックや箇条書きを直前で導入するときは、「**以下は**〜です」のように、これから何が続くかを明示してからつなげます。
- 画像を連続で並べません。各画像の直前に、その画像が何を示しているかの説明文を必ず入れます。
- 締め: 「おわりに」等のまとめ節を必ず設け、著者自身の考察・感想・今後の展望を書き、読者への誘導や挨拶で締めます。

## 3. Zenn特有のMarkdown記法
- 独自のメッセージ記法（要素の強調）を活用してください。
  :::message
  ここにメッセージを記述
  :::
- コードブロックには必ず言語名（例: ````ts````）を指定してください。

## 4. 補助スキルとの併用ルール

`.claude/skills/` に以下の2つのライティングスキルをインストールしている場合は、執筆・推敲の補助として使用します（k16shikano氏作。導入手順は `README.md` を参照）。

- `japanese-tech-writing`: 論証の厳密さ、LLMっぽい空句の禁止、冗長の排除、パラグラフライティング
- `cognitive-rhythm-writing`: 文章の緩急（認知リズム）の設計、執筆後の点検手順

**優先順位: 本ガイドライン（00_rules） > スキル。** 衝突する場合は本ガイドラインに従います。個別の衝突は以下の通り解決します。

| 論点 | 適用ルール |
|---|---|
| 導入・節頭の予告文 | 導入の「この記事では〜」の予告は本ガイドライン通り書く。セクション冒頭の一律の宣言は行わない（スキルの規範に従う）。予告を書く場合は態度のない議題表にせず、態度を帯びた一〜二文にする |
| 太字 | 本ガイドライン通り重要用語・機能名・製品名に使う。スキルの「一節に1〜2箇所」制限には従わない（ただし乱用はしない） |
| 読者への語りかけ | 本ガイドライン通り1セクション1回程度 |
| 節頭のつなぎ | 「次に、〜について解説します」のような平易な予告文でつないでよい。スキルの勧める反問・違和感・告白で開く形は、効果が明らかな箇所に限る（平易さを優先する） |
| 一文ごとに改行 | **従わない**（Zennは単一改行が`<br>`として表示されるため）。段落内は改行せず続けて書く |
| 文体 | 本ガイドライン通りです・ます調（スキルの例文はである調だが、原則のみ適用する） |
